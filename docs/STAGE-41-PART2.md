## 41.10 — категории банковских доходов с правилами

> **СДЕЛАНО ведущим в 41.10 (коммит после c8d383b): модель, движок, тесты `testIncomeCategories`, экран выбора в карточке, правила доходов в списке. Не переделывай; ниже — описание для справки. Используй `history.setIncomeCategory`, `history.incomeCategory(for:)`, `OperationIncomeCategoryView`. Для 41.12 перенос выборов должен включать и `incomeCategoryOverrides`.**

Сейчас доход получает категорию из `incomeSubcategoryOrder` по тексту (`FinancialEngine.incomeCategory`), у ручных доходов выбор есть, у банковских нет.

### Модель (`Models.swift`)
```swift
struct IncomeCategoryRule: Codable, Equatable, Identifiable {
    var id = UUID()
    var payeeKey: String      // FinancialEngine.counterpartyKey(operation.description)
    var title: String         // название операции, из которой сделано правило
    var category: String      // одна из FinancialEngine.incomeSubcategoryOrder
}
```
В `SavedHistory`: `var incomeCategoryRules: [IncomeCategoryRule]?` и `var incomeCategoryOverrides: [String: String]?` (identity банковской операции → категория дохода).

Методы `SavedHistory` (по образцу `setExpenseCategory`):
- `mutating func setIncomeCategory(_ category: String, for operation: BankOperation, forSender: Bool) -> Bool`
  - `false`, если категории нет в `incomeSubcategoryOrder` или операция не доход/проценты (`classify(...).type` не `.income`/`.interestIncome`);
  - ручной доход: меняет `subcategory` ручной операции;
  - `forSender == true` и ключ отправителя не пустой → правило (создать или заменить по `payeeKey`), индивидуальный выбор этой операции удалить;
  - иначе индивидуальный выбор в `incomeCategoryOverrides`.
- `mutating func removeIncomeCategoryRule(_ id: UUID)`.
- `func incomeCategory(for operation: BankOperation) -> String?` — текущая категория дохода (nil для не-дохода).

### Движок (`FinanceEngine.swift`)
- В `FinancialOperationInput` добавить `var incomeCategoryName: String? = nil` (значение по умолчанию — старые вызовы не ломаются).
- В `incomeCategory(for:assessment:)` самым первым: если `operation.incomeCategoryName` входит в `incomeSubcategoryOrder` **и** `assessment.type` — `.income` или `.interestIncome`, вернуть его. Затем прежний порядок (ручной префикс, текст).
- `classify` **не менять**. Назначенная категория не может превратить возврат, перевод между своими счетами, Сплит, незавершённую или отменённую операцию в доход (тест на каждый тип).
- Приоритет: индивидуальный выбор → правило отправителя → прежнее предположение.

### Подключение
- `ExpenseCategoryResolver.financialInput(for:)` (и `SavedHistory.financialInputs`) заполняют `incomeCategoryName` для доходов. Все места, где доходы группируются или ищутся (отчёты, поиск, `FinanceOperationSelection.matches` для дохода, кеш представления `FinancePresentationCache` — ключ кеша должен включать новые поля), берут `history.financialInput(for:)`/`financialInputs`.
- Карточка банковской операции: для дохода строка «Категория дохода» → выбор из `incomeSubcategoryOrder` с переключателем «Для всех поступлений от „<название>“» (включён по умолчанию, подпись: «Прошлые и будущие поступления этого отправителя тоже перейдут в эту категорию»). Для проценты/доход — одинаково.
- Экран «Категории расходов» → в раздел правил добавить «Правила доходов» (название → категория, удаление свайпом); показывать, если правила есть. (Можно назвать экран «Категории и правила», если проще.)
- Резервная копия: оба поля в копии; старые копии открываются.

### Тесты (`Tests/FinanceEngineTests.swift`, новая функция `testIncomeCategories`)
- без правок категории доходов и итоги — как раньше;
- правило отправителя меняет категорию всех его доходов (разные цифры в названии — тот же ключ), индивидуальный выбор сильнее правила;
- итог доходов периода не меняется от назначений;
- возврат / перевод между своими / Сплит / pending / расход не принимают категорию дохода (`false`, ничего не сохранено);
- удаление правила возвращает прежнее предположение;
- ручной доход меняет своё поле;
- копия туда-обратно; JSON без новых полей открывается.

## 41.11 — две PDF-выписки в одной истории

Сейчас: выбирается один PDF, и импорт **удаляет все операции до 01.10.2026** и заменяет их содержимым файла. Нужно выбрать несколько файлов за раз (выписка платёжного счёта + выписка вклада «Сейв»).

### Что нужно знать о «Сейве»
Формат выписки «Сейва» ты видишь только на личном файле пользователя (он лежит вне репозитория, путь спроси у пользователя или у него в iCloud Drive → Finance Test). Раскладку опиши в `docs/STATEMENT-FORMATS.md` **без** реальных названий и сумм (какие заголовки, колонки, как записана дата — одна дата без времени, как знаки сумм). Тест — только на синтетическом тексте, имитирующем эту раскладку.

### Разбор (`StatementImporter.swift`)
- `StatementImportResult` получает `source: Source` (`.account`, `.save`).
- `parsePages` сам определяет тип по содержимому (заголовки): платёжный счёт — как сейчас; «Сейв» — новый разбор. Неизвестный документ — прежняя ошибка «Это не похоже на выписку Яндекс Банка».
- **Идентификаторы выписки платёжного счёта не менять** (`statement-v1|…`, префикс `statement:`): иначе потеряются категории и правила пользователя. Для «Сейва» — свой префикс `statement-save:` (`statement-save-v1|…`), `paymentMethod` = «Сейв (выписка)», `timePrecision` = `statement_day`, время в `occurredAt` — 12:00 по Москве (чтобы часовые пояса не сдвигали день).
- «Сейв»: проценты (начисление/выплата) → `kind = interest_income`, это доход; пополнение вклада и вывод с вклада — собственные переводы (`internal_transfer`), **не доход и не расход**.
- Операции ≥ 01.10.2026 по-прежнему игнорируются обоим типам (`ignoredAtOrAfterCutoff`), пустая выписка и покрытие не до 30.09.2026 — ошибки как сейчас (для «Сейва» достаточно любого покрытия, но операций до 01.10.2026 хотя бы одна).

### Двойной учёт собственных переводов
Одно и то же перемещение «счёт → Сейв» встречается и в выписке платёжного счёта, и в выписке «Сейва». В движке уже есть `saveAccountSummary` и `isSaveTransfer`. Требование: после импорта обеих выписок **`report` (доходы/расходы) и `saveAccountSummary` не удваивают переводы**, а остаток карточного счёта (`Account.balance`, `tracksBankCard`) не меняется от строк «Сейва». Если для этого нужно менять `FinanceEngine.swift` (например, не считать строки с `paymentMethod == "Сейв (выписка)"` в `saveAccountSummary`/`accountBalance`) — сделай минимально, покрой тестом «обе выписки = только платёжная выписка плюс проценты». Если не получается без изменения формул — остановись и опиши ведущему.

### Объединение (`BankBrowser.swift`)
- Выбор нескольких PDF: `UIDocumentPickerViewController` с `allowsMultipleSelection = true` (и `fileImporter` в SwiftUI-версии, если выбор там).
- Новая точка входа: `importStatements(_ urls: [URL])`:
  1. Разобрать **все** файлы; любая ошибка → ничего не менять, показать, какой файл и почему.
  2. Два файла одного типа: объединить, дубли по `identity` убрать (одинаковые строки двух перекрывающихся выписок не должны задвоиться), тест.
  3. Заменяемые записи — **только своего источника**: для `.account` — как сейчас (все банковские операции раньше 01.10.2026, включая остатки сканирования, как и было); для `.save` — только операции с префиксом `statement-save:`. Выписка «Сейва» никогда не удаляет операции платёжного счёта, и наоборот не удаляет «Сейв» (если выбран только платёжный файл, записи «Сейва» остаются).
  4. Ручные операции, правила, выбранные категории, счета, группы, `categoryOverrides` — не трогать (кроме миграции из п. 41.12).
  5. Один `vault.save(next)`, затем `history = next`. `statementOperationCount` = число операций всех источников; `statementImportedAt` и `statementArchiveThrough` как сейчас.
- Повторный импорт тех же файлов даёт ту же историю (операций столько же, ни одной новой).
- Сообщение: «Импортировано: <N> операций платёжного счёта, <M> операций Сейва. Операций с 01.10.2026 оставлено сканеру: <K>».

### Тесты (`Tests/StatementImporterTests.swift`)
- «Сейв»: синтетическая выписка → проценты — доход, переводы — собственные;
- обе выписки вместе: итоги `report` = итоги одной платёжной выписки плюс проценты; `saveAccountSummary` и остаток карточного счёта не удваиваются;
- повторный импорт, перекрывающиеся выписки, только «Сейв» оставляет платёжные записи, только платёжная оставляет «Сейв»;
- ошибка в одном из файлов — история не изменена;
- идентификаторы платёжной выписки совпадают с прежними на старом тестовом файле (зафиксировать конкретные значения).

## 41.12 — строки PDF: описание, дата и сумма из одной физической строки

Проблема описана в `docs/STATEMENT-ROW-ISSUE.md`: `PDFPage.string` склеивает текст в порядке, который не совпадает со строками таблицы; регулярное выражение `rowRegex` цепляет описание соседней строки. Отсюда дата и сумма в `description`, а Сплит и собственные переводы получают тип расхода.

### Разбор
- Читать таблицу **по геометрии страницы**, а не по общей строке: для каждого символа брать `PDFPage.characterBounds(at:)` (через `page.string` индексы совпадают), собирать слова и группировать их в физические строки по близости вертикальной координаты; колонки определять по горизонтальным границам заголовков («Описание операции», «Дата и время операции», «Дата обработки», «Карта», «Сумма в валюте операции», «Сумма в валюте Договора»). Ячейка описания может занимать несколько строк — она принадлежит строке, у которой в колонках даты/суммы есть значения на тех же вертикальных границах.
- Парсер даёт **явное разделение**: `parsePages([String])` остаётся для старых текстовых тестов; новый `parseRows(_ pages: [[StatementCell]])`, где `StatementCell` — `(text, x, y, width, height)`. `importPDF` собирает ячейки из PDFKit и вызывает `parseRows`; текстовый путь используется только как запасной, если в документе нет геометрии.
- Валидация каждой строки: описание не должно содержать шаблонов `dd.MM.yyyy`, `в HH:mm`, суммы со знаком `₽` и номера карты в виде `*NNNN` отдельно. Если нашли — строка не принимается, импорт падает с понятным сообщением «Строка N страницы M разобрана неоднозначно», ничего не сохраняется.
- Идентификатор для **новых** правильных строк строится так же, как раньше (`statement-v1|date|time|processed|card|amount|description`), чтобы у уже правильных записей он не менялся.

### Тесты (CI, macOS)
Синтетический PDF создать в тесте через `CGContext`/`CTLine`: две выписки подряд, многострочные описания (2–4 строки), строки с карточным номером и без, платёж Сплита, возврат, перевод между своими, строки одинаковой суммы и даты подряд. Проверить: описание соответствует своей дате/сумме, типы (`installment_payment`, `refund`, `internal_transfer`) определены правильно, нет описаний с датами/суммами. Тест запускается в шаге «Проверка импорта выписки» workflow (PDFKit на Windows недоступен, локальный `check.ps1` его не выполняет — поэтому GitHub Actions обязательный).

### Миграция уже сохранённых записей
Нельзя просто пере-импортировать: идентификатор зависит от описания, поэтому пользовательские категории (`categoryOverrides`) потеряются. Правила миграции — часть `importStatements` при повторном выборе того же PDF:
1. Для **платёжного** источника: новые правильные записи заменяют старые `statement:` записи.
2. У каждой старой записи, чей `identity` отсутствует среди новых и у которой есть запись в `categoryOverrides` или `incomeCategoryOverrides`, ищется новая запись с тем же `occurredAt`, `amountKopecks` и `paymentMethod`; **только если такая ровно одна** (и её `identity` не занят другой старой записью) — переносим выбор на новый `identity`.
3. Неоднозначные (0 или больше одной новой записи с тем же ключом) выборы **не переносим и не угадываем**: считаем и показываем число.
4. Правила получателей (`categoryRules`, `incomeCategoryRules`) по ключу получателя не меняются; они сработают на исправленных названиях.
5. Показать итог до сохранения: диалог с числами «будет заменено записей / из них исправлены названия / выборов категорий перенесено / не перенесено (неоднозначно)» и кнопками «Применить» / «Отмена». Сохранение — одним `vault.save`, как в 41.11.

Тесты миграции: старая синтетическая запись с повреждённым описанием + новая правильная → один `identity`, категория перенесена; неоднозначный случай → выбор не перенесён, счётчик верный; ручные операции и правила не затронуты; повтор того же импорта ничего не меняет.

1. Доход от одного отправителя → другая категория, включён переключатель: все его поступления (прошлые и будущие) переехали; итог доходов не изменился. Возвраты и переводы между своими счетами по-прежнему не доходы.

4. Платежи Сплита и собственные переводы, которые раньше стали расходами из-за порчи описания, теперь показаны как Сплит и перемещение; в «Отчётах» расходы за старые месяцы изменились ровно на эти суммы.

7. Резервная копия: экспорт → восстановление — правила и выбранные категории доходов на месте.
